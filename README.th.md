Arak มาร์กข้อมูลส่วนบุคคล **ตั้งแต่ตอนที่โค้ดกำลังถูกเขียน** ไม่ใช่ในรายงาน CI สามสัปดาห์ถัดมา
ที่ไม่มีใครกลับไปอ่าน มันเก็บแคตตาล็อกของทุกฟิลด์ที่ถือข้อมูลส่วนบุคคล พร้อมวัตถุประสงค์
ฐานทางกฎหมาย และระยะเวลาเก็บ แล้วแปลงเป็นบันทึกรายการกิจกรรมการประมวลผล (RoPA) ตาม พ.ร.บ.
คุ้มครองข้อมูลส่วนบุคคล

มาในรูปปลั๊กอินสำหรับ Claude Code, คำสั่งบรรทัดคำสั่ง และไลบรารีตรวจข้อมูลส่วนบุคคลไทย

**ใช้ฟรีสำหรับงานส่วนตัว การศึกษา งานวิจัย และองค์กรไม่แสวงหากำไร ส่วนการใช้เชิงพาณิชย์ต้องมีสัญญา** —
ดู [COMMERCIAL.md](COMMERCIAL.md)

## ปัญหา

เครื่องมือความเป็นส่วนตัวทุกวันนี้เป็นการ **สแกนย้อนหลัง** รายงานโผล่มาตอนโค้ดขึ้นไปอยู่บน CI แล้ว
ซึ่งตอนนั้นฟิลด์นั้นถูกใช้งานไปทั่วระบบและไม่มีใครกลับไปแก้

จังหวะที่ถูกคือ **ตอนที่ฟิลด์เพิ่งถูกเขียนเสร็จ** ซึ่งเป็นจังหวะที่คนเขียน — หรือผู้ช่วย AI ที่เขียนแทน —
ยังจำได้ว่าฟิลด์นี้มีไว้ทำอะไร

และไม่มีเครื่องมือเจ้าไหนรู้จักกฎหมายไทย มาตรา 39 บังคับให้บันทึกครบเจ็ดหัวข้อ ตั้งแต่ข้อมูลที่เก็บ
วัตถุประสงค์ ผู้ควบคุม ระยะเวลาเก็บรักษา สิทธิและวิธีการเข้าถึง การเปิดเผยตามมาตรา 27
ไปจนถึงเงื่อนไขการปฏิเสธคำขอ บวกคำอธิบายมาตรการความมั่นคงปลอดภัยตามมาตรา 37

## ติดตั้ง

เปิด Claude Code ที่โปรเจกต์ที่อยากติดตั้ง แล้ว

```
/plugin marketplace add ksmaster03/arak
/plugin install arak@arak
```

รีสตาร์ต Claude Code แล้วสั่ง `/arak:setup`

เท่านี้จบ ปลั๊กอิน bundle ทั้งฮุก **และ** คำสั่ง `arak` ตัวเต็มไว้ในไฟล์ที่ไม่มี dependency เลย
จึงไม่ต้อง `npm install` ไม่ต้องแก้ `settings.json` เอง และไม่ต้องเพิ่มอะไรลง `PATH`

| คำสั่ง | ทำอะไร |
|---|---|
| `/arak:setup` | ตั้งค่าให้โปรเจกต์นี้ตั้งแต่ต้น แล้วช่วยเติมหัวข้อตามมาตรา 39 |
| `/arak:mark` | ไล่ปิดงานฟิลด์ที่ยังไม่ได้ตัดสินทีละตัว |
| `/arak:check` | ดูสถานะ และหาข้อมูลจริงที่ปนอยู่ในไฟล์ |

เครื่องมือความปลอดภัยที่แดงตั้งแต่วันแรก คือเครื่องมือที่ถูกปิดทิ้งในวันที่สอง

## การมาร์ก

เขียนไว้ในคอมเมนต์เอกสารของ Prisma ตรงเหนือฟิลด์ คำอธิบายภาษาคนที่มีอยู่แล้วไม่ต้องย้ายไปไหน

```prisma
model Customer {
  /// เลขประจำตัวผู้เสียภาษี ใช้ออกใบกำกับ
  /// @pii(category=government_id, purposes=tax_invoice)
  taxId String?

  /// @pii(category=contact, purposes=delivery;tax_invoice)
  email String?

  /// @pii(contact)
  phone String?

  /// @not-pii(reason="รหัสอ้างอิงภายใน สร้างแบบสุ่ม ไม่ผูกกับตัวบุคคล")
  refCode String
}
```

| คีย์ | ความหมาย |
|---|---|
| `category` | หมวดข้อมูล — ใส่เป็นค่าเดี่ยวแบบทางลัดก็ได้ `@pii(contact)` |
| `purposes` | อ้าง key ใน `purposes` ของแคตตาล็อก คั่นหลายอันด้วย `;` `\|` หรือ `+` |
| `retention` | ISO-8601 duration เช่น `P5Y` — ใส่เมื่อฟิลด์นี้ต่างจากค่าของวัตถุประสงค์ |
| `reason` | ใช้กับ `@not-pii` เท่านั้น |

หมวดแบ่งเป็นสองชุด ชุดทั่วไป — `identity` `government_id` `contact` `financial` `employment`
`education` `location` `device` `behavioral` `media` `family` `vehicle` `credential` —
และ **ชุดอ่อนไหวตามมาตรา 26** — `health` `disability` `belief_religion` `race_ethnicity`
`political_opinion` `sexual_behavior` `criminal_record` `union` `genetic` `biometric` —
ซึ่งถูกนับแยกเพราะต้องได้ความยินยอมโดยชัดแจ้ง

## แคตตาล็อก

`pii-catalog.yaml` คือแหล่งความจริงเพียงที่เดียว และเป็นไฟล์ที่อยู่ใน git

```yaml
purposes:
  - key: tax_invoice
    label: ออกใบกำกับภาษีและเก็บเอกสารตามกฎหมายบัญชี
    legalBasis: legal_obligation   # ม.24(6)
    retention: P5Y                 # ม.39(4)

fields:
  - id: prisma:Customer.taxId
    status: marked
    category: government_id
    purposes:
      - tax_invoice
    source:
      kind: prisma
      file: prisma/schema.prisma
      line: 29
      container: Customer
      field: taxId
```

สองส่วนนี้เจ้าของต่างกัน และเครื่องมือเคารพเส้นแบ่งนี้เคร่งครัด

- `controller` `purposes` `access` `securityMeasures` **เป็นของคน** เครื่องมือไม่แตะ
  และคอมเมนต์ที่เขียนไว้จะไม่หายตอน sync
- `fields` ถูกดูแลให้ตรงกับซอร์สเสมอ แต่ **ไม่ลบอะไรทิ้งเอง** ฟิลด์ที่หายจากโค้ดจะถูกทำเครื่องหมาย
  `orphaned` เพราะการที่โค้ดลบคอลัมน์ ไม่ได้แปลว่าข้อมูลที่อยู่เบื้องหลังถูกลบไปด้วย

## กฎการชี้ขาด

มีสามข้อ และมีแค่สามข้อ

1. ฟิลด์ที่มี `@pii(...)` ในโค้ด — **คำอธิบายในโค้ดชนะ** เพราะมันเดินทางไปพร้อมโค้ด
2. ไม่มี annotation แต่มีอยู่ในแคตตาล็อกแล้ว — **ของเดิมชนะ** เพราะคนเป็นคนใส่ไว้
3. ไม่มีทั้งสองอย่าง — ตัวเดาเสนอเข้ามาเป็น `unmarked` ให้คนตัดสิน

สถานะมีสี่แบบ `unmarked` (ใหม่ ยังไม่ตัดสิน — ฮุกทัก CI ตก) · `deferred` (หนี้เก่าที่รับรู้แล้ว —
ไม่ตื๊อ CI ผ่าน แต่ยังนับ) · `marked` · `not-pii` เมื่อคนตัดสินแล้ว ค่า `confidence` และ `detectedBy`
ของตัวเดาจะถูกลบทิ้ง ไม่ค้างไว้ให้คนอ่านคนถัดไปสับสน

**ข้อ 3 ไม่เคยถูกทำอัตโนมัติเกินระดับหมวด** หมวดข้อมูลอ่านจากโค้ดได้ แต่วัตถุประสงค์กับ
ฐานทางกฎหมายเป็นการตัดสินใจทางธุรกิจ ฟิลด์ `email` ที่เก็บไว้ส่งใบเสร็จ (ฐาน: สัญญา)
กับที่เก็บไว้ส่งโปรโมชัน (ฐาน: ความยินยอม) หน้าตาในโค้ดเหมือนกันทุกตัวอักษร แต่อยู่ใต้กฎหมายคนละข้อ
เมื่อไม่มีอะไรในแคตตาล็อกที่ตรง ปลั๊กอินจะหยุดแล้วถาม — RoPA ที่ดูเรียบร้อยแต่ผิด
อันตรายกว่าไม่มี RoPA เลย

## หาข้อมูลจริงที่ปนอยู่ในไฟล์

`sync` ดูแลว่า *สคีมา* ประกาศอะไรไว้ ส่วน `scan` ดูว่า *ไฟล์* มีข้อมูลของคนจริงปนอยู่ไหม —
สคริปต์ seed, fixture, ตัวอย่าง SQL, log ที่เผลอ commit ตามมา

```
$ arak scan

ที่พบ
  thai_national_id     11••••••••66     prisma/seed.ts:3:40
  thai_phone           08••••••••78     prisma/seed.ts:3:64
  email                so••••••••th     prisma/seed.ts:3:87
```

**ค่าจริงไม่เคยถูกพิมพ์ออกมา** เห็นแค่หัวกับท้าย เพราะ log ของ CI อยู่นานกว่าไฟล์ที่ถูกสแกนเสียอีก

ตัวตรวจอยู่ในแพ็กเกจ `@arak/detect-th` ซึ่งใช้แยกได้

| ชนิด | วิธีตรวจ |
|---|---|
| เลขประจำตัวประชาชน · เลขผู้เสียภาษี | สิบสามหลัก **พร้อมตรวจหลักตรวจสอบ** จึงคัดรหัสอ้างอิงสุ่มทิ้งได้ราว 91% |
| เบอร์โทร | ตรวจโครงสร้างจริง มือถือ 06/08/09 ตามด้วยแปดหลัก รองรับ `+66` |
| อีเมล · IPv4 | ตามรูปแบบมาตรฐาน |
| ชื่อคนไทย | อาศัยคำนำหน้า นาย นาง นางสาว น.ส. ด.ช. ด.ญ. |
| ที่อยู่ไทย | ต. อ. จ. แขวง เขต ซอย หมู่ ถนน — ส่วนที่ติดกันถูกรวมเป็นที่อยู่เดียว |
| ป้ายทะเบียนรถ | พยัญชนะไทยสองตัว มีหรือไม่มีเลขนำหน้าก็ได้ |
| บัตรเครดิต | สิบสี่ถึงสิบเก้าหลักพร้อม Luhn |
| หนังสือเดินทาง · เลขบัญชี · รหัสไปรษณีย์ | **ต้องมีคำบริบทอยู่ใกล้เท่านั้น** ไม่งั้นผลบวกลวงท่วม |

> หลักตรวจสอบของเลขบัตรประชาชนมีจุดบอดที่วัดแล้ว — หลักที่สามมีน้ำหนัก 11 ซึ่งหารด้วย 11 ลงตัว
> จึงไม่มีผลต่อเศษเลย **แก้หลักที่สามเป็นอะไรก็ได้ สูตรจับไม่ได้สักกรณี** ส่วนหลักอื่นหลุดราว 1.7%
> ใช้คัดกรองได้ แต่ใช้ยืนยันตัวตนไม่ได้

ไฟล์ที่ตั้งใจให้มีข้อมูลรูปร่างเหมือนของจริง สั่งข้ามได้

```yaml
scan:
  ignore:
    - "**/test/**"
```

หรือ `--ignore "<glob>"` จากบรรทัดคำสั่ง ใส่ซ้ำได้

## ด่าน CI

```yaml
- run: node packages/cli/dist/index.js status
```

- `0` — ฟิลด์ใหม่ถูกตัดสินครบแล้ว
- `1` — ยังมีฟิลด์ที่ไม่ได้ตัดสิน หรือแคตตาล็อกมีข้อผิดพลาด เช่นมาร์กว่าเป็นข้อมูลส่วนบุคคลแล้ว
  แต่ไม่ระบุวัตถุประสงค์ (มาตรา 39(2) บังคับ)
- `2` — เรียกใช้ผิด หรืออ่านไฟล์ไม่ได้

ใส่ `--strict` เมื่ออยากให้หนี้เก่าทำให้ตกด้วย ตอนที่ทีมพร้อมไล่เคลียร์
ใช้ `sync --check` เมื่ออยากบังคับว่าแคตตาล็อกที่ commit ไว้ต้องตรงกับสคีมาเสมอ

## สถานะ

รองรับ TypeScript + Prisma เป็นสแตกชุดแรก

| ทำแล้ว | ยังไม่ทำ |
|---|---|
| สคีมาแคตตาล็อกครบตามมาตรา 39 | ตัวสร้างเอกสาร RoPA (.docx/.xlsx) |
| ตัวอ่านสคีมา Prisma พร้อม `@pii` | กฎ Semgrep ห้ามข้อมูลส่วนบุคคลไหลลง log |
| เขียนแคตตาล็อกกลับโดยคอมเมนต์ไม่หาย | MCP server อ่านไฟล์แบบปิดบัง |
| ตัวเดาจากชื่อฟิลด์ 39 กฎ | ตัวอ่าน OpenAPI และ TypeScript type |
| ตัวตรวจค่าจริงของไทย 12 ชนิด | ชื่อไทยที่ไม่มีคำนำหน้า |
| ตัวปิดบังที่ให้ตัวแทนคงที่และแปลงกลับได้ | ปล่อยขึ้น npm และ marketplace สาธารณะ |
| ฮุก Claude Code สามตัว พร้อมเส้นฐาน | |
| `init` / `sync` / `baseline` / `status` / `scan` | |

ตัวเดาจากชื่อฟิลด์อ่านแค่ชื่อกับชนิดข้อมูล มีไว้เพื่อให้มีของให้ตัดสินตั้งแต่วันแรก
และทุกกฎในนั้นถูกปรับจากการรันกับสคีมาการผลิตจริงสี่ชุด — ระบบคลังสินค้า ระบบซ่อมบำรุง ระบบบุคคล
และสคีมาคลินิกใน `arak-sandbox`

ปลั๊กอินถูก bundle ด้วย esbuild เป็นไฟล์เดียวต่อจุดเข้า **โดยตั้งใจ** เพราะ Claude Code ติดตั้ง
ปลั๊กอินด้วยการคัดลอกเฉพาะโฟลเดอร์ปลั๊กอินไปไว้ในแคช และโหมด link ใช้บนวินโดวส์ไม่ได้
ถ้ายัง import ข้ามไปแพ็กเกจอื่นในเวิร์กสเปซ ตัวที่ถูกคัดลอกไปจะพังทันที

กฎของตัวตรวจทุกข้อถูกปรับจากข้อมูลจริง ไม่ใช่จากการนั่งเดา ทุกครั้งที่แก้กฎเพราะเจอเคสจริง
**ให้เพิ่มเคสนั้นลงเทสต์พร้อมคอมเมนต์ว่าเจอมาจากไหน**
